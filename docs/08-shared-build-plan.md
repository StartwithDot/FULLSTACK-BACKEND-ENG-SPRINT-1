# From practice to one shared product

Each student attempts the core skill. The build pair promotes the smallest reviewed implementation, and another pair checks it. Reuse successful individual work, attribute original authors and keep the promotion in the weekly time budget.

| Week                      | Project need                                                                                                   | Shared paths                                                                                                          | Demonstrable outcome                                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| [1](../weeks/week-01.md)  | The client needs one place to inspect sandbox payment events, but the request is not yet a specification.      | `shared/delivery/brief.md and shared/delivery/context.md`                                                             | A reviewed brief, a safe event summary, and one authored pull request. Milestone: Agreed client brief.                |
| [2](../weeks/week-02.md)  | The merchant needs event counts, while fields such as amounts and event kinds need an agreed meaning.          | `shared/delivery/event-contract.md and shared/database/practice-notes.md`                                             | Typed event data, real SQL answers and an explicit input contract.                                                    |
| [3](../weeks/week-03.md)  | The event contract must become reusable checks, and events must remain attached to a real merchant.            | `shared/delivery/data-model.md and shared/api/test/contract.test.ts`                                                  | A reusable validation exercise, a relational model and tests that detect a bug.                                       |
| [4](../weeks/week-04.md)  | Another program must send or request events without sharing the API's memory.                                  | `shared/api/src/app.ts and shared/delivery/api-contract.md`                                                           | A tiny HTTP application, observable async behavior and an API plan.                                                   |
| [5](../weeks/week-05.md)  | The merchant must accept a useful event and reject malformed input consistently.                               | `shared/api/src/routes/events.ts, shared/simulator/send-event.ts and shared/delivery/first-flow.md`                   | A simulator request reaches the API and is visible through a list endpoint. Milestone: First local event flow.        |
| [6](../weeks/week-06.md)  | Restarting the API currently loses all accepted events.                                                        | `shared/database/migrations/, shared/api/src/repository.ts and shared/api/test/persistence.db.test.ts`                | A fresh migration, parameterized storage and a restart proof. Milestone: Durable event flow.                          |
| [7](../weeks/week-07.md)  | Repeated event IDs can create duplicate records, and an unbounded list can grow without limit.                 | `shared/database/migrations/002-event-identity.sql, shared/api/src/repository.ts and shared/api/src/routes/events.ts` | Database-backed duplicate behavior and a stable, bounded listing contract.                                            |
| [8](../weeks/week-08.md)  | The API must distinguish a signed-in operator from an anonymous request before exposing merchant data.         | `shared/database/migrations/003-operators.sql, shared/api/src/auth.ts and shared/delivery/security-model.md`          | Login, expiry and logout with protected API access.                                                                   |
| [9](../weeks/week-09.md)  | A signed-in operator must not see or write another merchant's events.                                          | `shared/api/src/routes/events.ts, shared/api/test/ownership.db.test.ts and shared/simulator/send-event.ts`            | A working authenticated event API with cross-merchant rejection. Milestone: Protected merchant flow.                  |
| [10](../weeks/week-10.md) | A merchant needs to inspect event data without typing curl commands; backend responses must stay safe.         | `shared/web/src/App.tsx, shared/web/src/EventList.tsx and shared/api/src/routes/events.ts`                            | Typed UI components and bounded safe API responses.                                                                   |
| [11](../weeks/week-11.md) | The interface currently shows static data and needs real authenticated event queries.                          | `shared/web/src/api.ts, shared/web/src/App.tsx and shared/delivery/browser-flow.md`                                   | A signed-in merchant can inspect its own persisted events through React.                                              |
| [12](../weeks/week-12.md) | The happy-path demo works, but duplicates, transactions and regressions need trustworthy checks.               | `shared/api/test/, shared/database/README.md and shared/delivery/test-matrix.md`                                      | A coherent test matrix, one exercised transaction and corrected weak cases.                                           |
| [13](../weeks/week-13.md) | A slow database, bad request or expired session should produce a useful failure rather than a misleading demo. | `shared/api/src/app.ts, shared/api/test/, shared/web/src/App.tsx and .github/workflows/checks.yml`                    | Bounded endpoints, redacted diagnostic logs and deliberate client errors.                                             |
| [14](../weeks/week-14.md) | The application must be maintainable when something fails and when a different person starts it.               | `shared/delivery/incident.md, shared/database/migrations/ and shared/delivery/runbook.md`                             | An evidence-led repair, an explained query plan and a corrected runbook.                                              |
| [15](../weeks/week-15.md) | The product and learning evidence must survive the original builders and continue into Sprint 2.               | `shared/delivery/runbook.md, shared/delivery/final-architecture.md, shared/delivery/demo.md and README.md`            | A reproducible local product, an honest demo and attributable contribution evidence. Milestone: Independent handover. |

Shared product files not present in the starter are created by students at the named week. Placeholder code is not a finished application or an assessment answer. Maintain API/schema compatibility deliberately and add forward migrations after a migration has been shared.

Use the [individual wiring guide](14-individual-app-wiring.md) to assemble your own continuing app through those same tasks. The [PayHook handoff](13-payhook-handoff.md) defines the next-sprint service boundary; it does not add implementation tasks here.

All ten students learn all core work even when only two author that week's shared PR. Every student serves on three build rotations. Review and witness evidence belongs in the per-week log, not an invented completion claim.
